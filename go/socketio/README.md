# socketio

The Socket.IO v4 / Engine.IO v4 implementation for Go that the Go code generated by
socketrpc-gen is written against: `servers/socket` for a generated server, `clients/socket`
for a generated client.

```
go get github.com/nguyenvanduocit/socketrpc-gen/go/socketio
```

| Package | Provides |
|---|---|
| `servers/socket`, `servers/engine` | Socket.IO and Engine.IO servers |
| `clients/socket`, `clients/engine` | Socket.IO and Engine.IO clients |
| `parsers/socket`, `parsers/engine` | wire encoders and decoders |
| `pkg/...` | event emitter, types, queues and utilities shared by all of the above |

## Origin

This module began as a copy of [zishang520/socket.io](https://github.com/zishang520/socket.io)
v3.0.6, MIT-licensed (see `LICENSE`, which keeps the original copyright). Its seven modules are
one module here; package names and APIs are the same, so upstream documentation applies.

Changes since the copy:

- `clients/socket.Manager.Open` attaches its `open`/`error` listeners to the engine socket
  before the transport starts. It used to start the transport first, so a connection that opened
  inside that window was never sent the Socket.IO CONNECT packet and stayed disconnected
  (about 1 in 350 connections under load). `clients/socket/connect_race_test.go` drives 2000
  concurrent connections and requires every one to connect.
- `servers/socket` namespace `_doConnect` registers a connecting socket with its client before
  the socket writes its CONNECT packet. It used to register after, so with a middleware
  (`Server.Use`) a peer that emitted as soon as it read CONNECT could have that first event
  decoded before the registration, and the client closed the connection ("invalid state").
  `servers/socket/connect_ack_test.go` holds the server right after CONNECT leaves it.
- `clients/engine.SocketWithoutUpgrade` gains `MaxPayload() int64`: the largest packet the server
  accepts, as it advertised in the handshake (`maxPayload`, the server's `MaxHttpBufferSize`), or
  -1 before the handshake. The client stored the value but had no accessor, so a caller could not
  refuse an oversized packet itself and the server closed the WebSocket with 1009 instead,
  dropping every call in flight. `clients/socket/max_payload_test.go` reads it back from a server
  configured with a non-default limit.
- `clients/socket` reads the `data` of a CONNECT_ERROR packet as optional. It used to require a
  value, so a refusal without data (`NewExtendedError(message, nil)`, which encodes data as null)
  reached `connect_error` as a parse error instead of the server's message.
  `clients/socket/connect_error_test.go` refuses a handshake that way.
- `clients/socket.Socket` sends one CONNECT per engine session. `Connect` subscribes to the
  Manager's `open`, opens the Manager, and connects at once if the Manager is already open; the
  Manager opens on another goroutine, so it could open in between and the socket sent CONNECT
  from both. The server then either accepted a second connection for the same client or closed
  the connection on the duplicate ("invalid state"), dropping a socket that had just reported
  `connect` (about 1 in 30,000 connections under load). `clients/socket/connect_once_test.go`
  opens the Manager inside that window every time and requires one server-side connection.
- `clients/engine` WebSocket transport is open, and so writable, before it reads its first
  message. It started reading first, so the server's handshake could open the engine while the
  transport was still opening; the CONNECT the socket wrote then waited in the engine's buffer for
  a flush nothing triggered, and the connection never reached `connect`. The duplicate CONNECT
  above had been rescuing most such connections. `clients/socket/connect_race_test.go` covers it.
- `clients/engine` tries its transports in a fixed order: polling, websocket, webtransport, as
  engine.io-client does, with any other transport after them by name. Transports are configured as
  a set, and the order used to come from the set's map, so about one connection in ten with the
  default transports tried WebTransport first and, against a server without HTTP/3, waited for the
  QUIC idle timeout instead of connecting. Upgrades still go only to transports the server offers.
  `clients/engine/transport_order_test.go` builds the try-order a hundred times per case, and
  `clients/socket/default_transports_test.go` connects 500 times with the default options to a
  server without HTTP/3 and requires every connection to connect and answer a call.
- `clients/engine` polling transport keeps one long-poll GET in flight on its own goroutine and
  sends POST writes beside it, one at a time, as engine.io-client does. The GET used to run on the
  write queue, so every write, CONNECT included, waited until the server answered the pending poll,
  which an idle server does only when it next pings; a polling-only client's acknowledged call
  timed out. `clients/socket/polling_test.go` makes three calls over polling alone with the ping
  interval far above the call timeout.
- `clients/engine` polling transport's `Pause`, which an upgrade to websocket waits on, looks at the
  poll and the write in flight and subscribes to their completion in one step under a lock, under
  which each completion changes its state and the next poll is decided. It used to look first and
  subscribe after, so a poll answered or a write finished in between was never seen: the pause
  never completed, the upgrade stalled, and every packet written after it stayed in the socket's
  buffer (about one connection in 500 with the default transports).
  `clients/engine/polling_pause_test.go` pauses while a server answers every poll at once.
- `clients/socket.Manager` delivers the engine's close, and a parse error, through the same queue
  as the packets read before it, and drops every queued task whose engine session is no longer the
  open one. The close used to be handled on the goroutine that closed the engine, so a CONNECT read
  just before the transport dropped reached the socket after its `disconnect`, and the socket
  reported connected on a dead engine until the next reconnect.
  `clients/socket/close_order_test.go` closes the engine while the CONNECT is being delivered.
- `clients/socket.Socket.NoBuffer()` is a per-emit flag, like `Volatile` and `Timeout`: when the
  socket is not connected as `Emit` runs, the packet is not buffered for the next connection, and
  its acknowledgement, if any, is called before `Emit` returns with `socket has been disconnected`.
  A NoBuffer emit bypasses the retry queue. `Emit` decides to send, buffer or refuse under the same
  lock under which `onclose` and `onconnect` change the connected state, so the decision cannot be
  made against a state that changes before the packet is written. Without the flag a call made
  after the connection dropped is buffered, and runs on the next connection even when its caller
  has already reported it failed. `clients/socket/no_buffer_test.go` emits from the `disconnect`
  listener and requires the server to receive nothing after the reconnect.
- `clients/socket` binds the acknowledgement it hands an inbound event to the engine session the
  event arrived on: the ACK is written on that session, and dropped if the Manager has moved to
  another since. It used to be written to whatever engine was current, and a server numbers its
  calls per namespace from zero, so an answer that crossed a reconnect, to a restarted server in
  particular, settled the new server's call with the same id.
  `clients/socket/ack_session_test.go` answers a call after the server restarts.
- `pkg/types.HttpServer.Listen` and `ListenTLS` bind the address before they call back and emit
  `listening`, and serve on another goroutine after. They used to start the server on that
  goroutine and call back at once, so a client started from the callback could be refused (about
  one start in ten on an idle machine, more under load). `pkg/types/http-server_test.go` dials
  from the callback and from a `listening` listener.
- `clients/socket.WebSocketOnly()` returns the transport set holding WebSocket alone, for a
  client that should connect straight over WebSocket. A generated Go client's `Dial` uses it
  when its caller sets no transports.

## Stress testing

Every closed connection holds its local port in TIME_WAIT for 2×MSL (30 s on macOS), and the
ephemeral range is 16,384 ports. A WebSocket-only dial leaves one such port behind; one that
starts on long-polling and upgrades leaves about 2.5. Thousands of dials repeated faster than
that drain exhaust the range, and the next dial fails with `connect: can't assign requested
address` — a generated client's `Dial` reports it as TIMEOUT with that `last connect error`.
Check `netstat -an -p tcp | grep -c TIME_WAIT` before reading such a failure as a library bug.
